# GETGO V2.0 产品需求文档

**版本：** V2.0

**版本主题：** 自适应技能学习与有限自治 Learning Agent

**迭代性质：** 重大产品版本迭代

## 1. 开发前置要求

本次任务是在现有 GETGO V1 基础上进行产品迭代，而不是重新开发项目。

开始实现前，阅读项目中的：

- `AGENTS.md`
- `docs/prd.md`
- `docs/decisions.md`
- 其他已有的开发、架构及阶段记录文档
- 学习路线生成、学习页面、学习进度管理、AI 答疑相关代码

理解现有产品逻辑、数据结构和技术架构后再进行修改。

尽可能复用现有组件、Service、API、模型调用机制、资料引用机制和轻量 RAG 能力，避免不必要的架构重构。

本次任务需要完成实际功能开发及项目文档更新，而不仅仅是输出实现计划。

本次暂不开展系统化 AI 效果评测、竞品对照实验及用户价值量化实验，但需要完成必要的功能测试与回归测试，确保新版本可以正常运行。

## 2. 迭代背景与产品决策

### 2.1 V1 产品定位及核心假设

GETGO V1 面向存在碎片化学习资料囤积、信息过载和学习启动困难问题的技能自学者。

通过 AI 对用户输入的学习资料进行理解、分类、重组和路线规划，将无序资料转化为结构化、可执行、可溯源的学习任务，降低用户的学习启动门槛。

V1 的核心产品假设是：

用户难以开始学习的主要原因之一是信息过载和缺乏明确的学习路径，因此通过 AI 生成学习路线，可以降低用户的学习决策成本并推动其开始学习。

### 2.2 V1 用户反馈与问题发现

在 V1 的用户验证过程中，用户表现出使用产品的意愿，认可将碎片化资料整理为学习路线的产品价值。

但大多数用户在完成几个学习步骤后便停止使用产品，未能形成持续使用行为，使 GETGO 实际上更接近一个一次性的学习规划工具，而不是一个能够持续陪伴用户学习的工具。

结合进一步的用户需求确认，发现以下问题：

**问题一：线性任务路线与技能学习的实际特点不完全匹配。**

绘画、乐器等实践型技能并非完成一个任务后即可永久进入下一任务。

部分基础能力需要在一段时间内反复练习，并且可以与其他学习任务并行进行。

例如：

- 吉他基础指法需要持续练习。
- 和弦转换需要多次重复才能逐渐熟练。
- 绘画中的线条控制、排线和形体观察需要长期训练。
- 用户完成一次练习，不代表已经掌握对应能力。

V1 的线性任务完成机制无法充分表达这种学习过程。

**问题二：静态学习路线无法充分适应用户实际学习情况。**

AI 在生成初始学习路线时，无法准确预知用户的实际学习速度、理解能力、练习效果及后续遇到的困难。

当用户反复无法完成任务，或者在答疑过程中表现出明显的学习困难时，原有学习路线仍可能保持不变。

用户需要自行判断是否继续练习、降低难度、跳过任务或重新安排学习内容。这使学习过程中的决策负担重新回到了用户身上。

以上问题是本次迭代重点解决的产品问题。暂不将其描述为已经通过量化实验确认的唯一流失原因，也不编造用户样本量、留存率等具体数据。

### 2.3 核心需求重新定义

V1 主要解决学习开始之前的决策困难。

V2 在保留这一核心价值的基础上，进一步解决学习过程中的持续决策困难。

用户不仅需要知道应该从哪里开始，还需要知道：

- 今天应该学习什么？
- 哪些基础能力需要继续练习？
- 遇到困难时应该如何调整？
- 当前学习进度是否需要改变？
- 今天没有完成全部任务，明天应该如何继续？

用户希望 GETGO 不只是生成一份学习计划，而是更像一个能够手把手引导自己前进的老师。

### 2.4 V2 产品定位

GETGO 是一个面向技能自学者的自适应 AI 学习 Agent。

产品将用户的碎片化学习资料转化为可执行的学习路线，通过每日学习任务、周期性练习和基于学习反馈的有限自治教学决策，帮助用户从资料收藏走向持续学习与技能掌握。

核心价值从降低学习启动成本，进一步延伸至降低持续学习过程中的决策成本。

### 2.5 本次迭代目标

1. 使学习任务结构更加符合实践型技能的学习特点。
2. 通过每日学习机制降低用户持续使用产品的行动门槛。
3. 允许用户在未完成全部任务的情况下继续后续学习，不因单日任务未完成而中断整个学习流程。
4. 使 AI 能够观察用户的实际学习情况，在必要时主动进行教学干预。
5. 让产品从一次性的学习路线生成工具，升级为具有有限自治能力的持续学习助手。

- 初始学习路线 Workflow 调整。
- 一次性学习任务与周期性练习任务分类。
- 今日学习任务生成与展示。
- 学习日切换及未完成任务处理。

- Agent 决策记录与学习计划调整记录。

- 多 Agent 协作。

- 日历集成、消息推送及后台定时任务。

- 后续追加学习资料并重新生成整体路线。
- 系统化 AI 评测体系及用户实验。

保持项目轻量级 Demo 的定位。不为了展示技术复杂度而增加与本次核心产品目标无关的功能。

## 4. 产品整体架构

V2 采用 Workflow、确定性程序逻辑与有限 Agent 相结合的混合架构。

### 4.1 Workflow 职责

沿用并调整现有初始学习路线生成流程：

用户输入资料 → 多模态资料理解 → 主题识别 → 学习路线规划与任务分类 → 独立核验 → 结构化学习计划输出。

Workflow 负责生成初始学习路线，识别不同性质的学习任务，并建立基本的任务依赖关系及周期练习安排。

初始学习路线仍然是整个学习过程的基础。

### 4.2 确定性程序职责

程序负责：

- 今日学习任务组装。
- 周期性练习任务调度。
- 学习日切换。
- 每日任务完成情况记录。
- 学习历史保存。
- 任务状态管理。
- Agent 行动参数校验。
- 学习计划变更应用与撤销。
- 保证数据一致性。

对于能够通过明确逻辑实现的功能，不额外调用大模型。

### 4.3 Learning Agent 职责

Agent 负责：

- 理解用户当前及历史学习状态。
- 理解用户在 AI 答疑过程中体现出的学习困难。
- 判断是否需要教学干预。
- 自主选择合适的教学行动。
- 在必要时调整后续学习任务。
- 观察教学行动结果及用户的后续反馈。
- 判断是否需要进一步行动。

Agent 不负责每日任务的常规机械调度，也不需要重新生成全部学习路线。

### 4.4 整体学习闭环

初始学习路线生成

→ 今日学习任务

→ 用户学习、练习及 AI 答疑

→ 记录任务完成情况和问答历史

→ Agent 观察学习状态

→ 自主判断是否需要干预

→ 保持原计划或执行有限教学行动

→ 更新后续学习安排

→ 继续观察新的学习反馈

## 5. 功能需求一：初始学习路线 Workflow 调整

### 5.1 学习任务类型

将现有学习路线任务区分为两种基本类型。

#### A. 一次性学习任务（One-time Task）

适用于能够通过一次相对完整的学习或实践完成的任务。

例如：

- 认识吉他的基本结构。
- 理解六线谱的阅读方法。
- 了解基础透视原理。
- 完成第一次基础和弦学习。

一次性任务完成后，默认不再出现在后续每日任务中。

如果 Agent 判断用户需要重新学习，可以通过合法的教学行动重新安排相关内容，但不能随意删除或覆盖历史完成记录。

#### B. 周期性练习任务（Recurring Practice）

适用于需要重复训练、逐步提升熟练程度的任务。

例如：

- 吉他基础指法练习。
- 和弦转换练习。
- 节奏稳定性练习。
- 绘画线条控制练习。
- 基础形体观察与描绘练习。

周期性任务在单日完成后，仍然可以在后续学习日继续出现。

周期性任务可以与一次性学习任务并行存在。

### 5.2 任务结构要求

在现有任务数据结构基础上进行最小必要扩展。

每个任务应能够表达以下信息：

- 唯一任务 ID。
- 任务名称。
- 任务类型。
- 学习目标。
- 具体操作步骤。
- 建议学习或练习时长。
- 单次任务完成标准。
- 必要的前置任务依赖。
- 原始学习资料引用。
- 当前任务状态。

周期性练习任务额外包含：

- 开始练习的条件。
- 建议练习频率。
- 初始练习周期或建议复核节点。
- 持续练习目标。
- 停止、减少或调整练习的参考条件。

V2 不要求建立复杂的技能掌握度模型。

不应直接根据累计练习次数或任务完成次数推断用户已经掌握对应技能。

具体字段名称、类型及存储方式应结合现有项目结构确定，避免为了满足文档中的概念而重复建立已有字段。

### 5.3 AI 生成要求

调整现有学习路线生成 Prompt、结构化输出及独立核验逻辑，使 AI 能够：

1. 根据资料内容识别适合重复练习的知识点或技能。
2. 判断哪些任务适合一次性完成，哪些需要周期性安排。
3. 为周期性练习生成合理的练习方式、频率、时长及完成标准。
4. 识别必要的前置任务依赖。
5. 允许周期性练习与新知识学习并行进行。
6. 保持现有资料引用及内容真实性要求。

不强制所有学习路线都必须包含周期性任务。

对于不需要反复练习的学习内容，允许全部生成一次性任务。

如果原始资料没有明确给出练习周期或频率，AI 可以提供合理的教学建议，但应区分原始资料内容与 AI 推导出的练习安排，不得为推导内容伪造资料引用。

### 5.4 独立核验要求

在已有核验逻辑基础上增加必要检查：

- 任务类型是否合理。
- 是否存在明显不合理的周期性练习。
- 是否存在循环或无效的前置依赖。
- 周期任务是否包含可执行的练习内容。
- 任务完成标准是否明确。
- 资料引用是否有效。
- 是否存在明显知识错误或无依据的事实陈述。

不额外引入复杂的多轮核验系统。

## 6. 功能需求二：今日学习机制

### 6.1 页面定位

将每日学习任务作为正式学习阶段的主要交互界面。

用户进入学习页面时，默认看到当前学习日需要完成的任务，而不是要求用户从完整学习路线中自行选择下一项任务。

完整学习路线仍然保留，用于查看：

- 整体学习目标。
- 当前学习阶段。
- 已完成的一次性任务。
- 后续学习内容。
- 正在持续进行的周期练习。

整体路线作为全局参考，今日任务作为主要行动入口。

### 6.2 今日学习页面

页面至少包含：

- 当前学习主题。
- 当前学习日，例如 Day 1、Day 2。
- 今日预计学习时长。
- 今日任务完成情况。
- 今日周期性练习任务。
- 今日一次性学习任务。
- 当前任务详细内容与资料引用。
- 现有 AI 助手入口。
- 进入下一学习日的操作入口。
- Agent 教学提示或学习调整信息（如有）。

优先沿用现有产品视觉风格和任务组件，不进行无必要的整体 UI 重构。

### 6.3 今日任务生成逻辑

今日任务由程序根据当前有效学习计划、任务状态和练习调度信息组装。

今日任务包括：

A. 当前符合执行条件的周期性练习。

B. 当前符合前置依赖关系的一次性学习任务。

C. 此前未完成且仍有必要继续执行的任务。

D. Agent 已生效的教学调整任务。

今日任务数量及建议时长应保持合理，避免将所有未完成任务无限累积到后续日期。

初始计划中的任务时长、顺序和调度信息由 Workflow 提供，日常组装由程序执行。

不需要每天重新调用模型生成整份学习计划。

### 6.4 学习日定义

V2 使用用户主动推进的学习日机制。

Day N 表示第 N 个学习单元或学习日，而不强制绑定自然日期。

用户可以在任意时间主动进入下一学习日，便于实际学习和 Demo 演示。

同时可以记录真实操作时间，用于区分学习日推进次数与自然时间流逝。

如果用户在同一天连续推进多个学习日，Agent 不应将其误判为已经完成了数个自然日的练习。

不实现后台自动跨日刷新。

### 6.5 进入下一学习日

用户即使没有完成今日全部任务，也必须能够主动进入下一学习日。

不得将完成全部今日任务设置为进入下一日的必要条件。

进入下一学习日时：

1. 保存今日任务完成情况。
2. 保存与当前学习日相关的 AI 问答记录。
3. 保留未完成任务状态。
4. 更新学习日编号。
5. 根据有效学习计划和任务状态生成下一学习日的任务。
6. 在合适的观察节点调用 Learning Agent 判断是否需要干预。

如果存在未完成任务，可以通过轻量提示告知用户，但不应阻止其继续学习。

### 6.6 未完成任务处理

未完成的一次性任务：

- 不自动标记为已完成。
- 保留原有状态与前置依赖关系。
- 根据后续安排再次出现在适合的学习日。
- 不阻止其他无直接依赖关系的任务推进。

未完成的周期性任务：

- 记录本学习日未完成。
- 保留后续正常练习安排。
- 不因漏练一次而自动增加双倍练习量。
- 不默认判定用户能力下降或学习失败。

如果某任务持续未完成，或者用户在答疑过程中反复表现出相关困难，该记录应成为 Agent 的观察依据。

未完成任务的日常调度不等同于 Agent 修改学习计划。

### 6.7 每日任务状态

区分学习计划中的任务定义与某个学习日中的任务实例。

例如：

同一个“基础指法练习”周期任务，可以在 Day 1、Day 2、Day 3 分别产生独立的练习实例。

完成 Day 1 的练习实例，不代表之后的周期任务全部完成。

保存每日任务实例的完成情况，避免后续计划调整导致历史学习记录发生改变。

## 7. 功能需求三：有限自治 Learning Agent

### 7.1 功能定位

Learning Agent 是 V2 新增的教学决策模块。

Agent 不只是回答用户的问题，而是能够综合用户的学习行为、历史信息及 AI 问答内容，判断用户是否出现需要教学干预的情况，并选择合适行动。

Agent 应表现得像一个相对稳定、有耐心、了解学生近期学习情况的老师。

默认尊重原有学习路线，不为了体现智能程度而频繁调整计划。

### 7.2 Agent 可观察的信息

Agent 的主要观察依据为以下两类信息。

#### A. 每日任务完成情况

包括但不限于：

- 当前学习日。
- 今日任务及完成状态。
- 历史学习日任务完成情况。
- 周期性任务的历史完成记录。
- 持续未完成的任务。
- 一次性任务的学习进度。
- 当前阶段与前置依赖关系。
- 已执行的教学调整及后续表现。

#### B. AI 助手问答记录

包括但不限于：

- 用户针对学习任务提出的问题。
- 用户明确表达的困难、困惑与时间限制。
- 用户反复询问的知识点。
- AI 助手已提供的解释和学习建议。
- 与当前任务或历史任务有关的上下文。

Agent 同时可以读取完成教学决策所必需的初始学习计划、当前有效学习计划及相关原始资料。

不新增复杂的用户画像系统。

主要通过现有任务数据和问答记录形成对用户学习状态的判断。

### 7.3 问答记录要求

沿用现有 AI 助手能力及轻量 RAG 机制。

补充必要的历史记录保存机制，使 AI 问答尽可能关联：

- 学习项目 ID。
- 学习日。
- 当前任务 ID（如有）。
- 用户问题。
- AI 回答。
- 消息时间。

Agent 应重点理解用户的问题、困难及行为证据。

AI 助手此前生成的回答可以作为已经提供过哪些帮助的记录，但不能直接作为用户已经掌握技能的证明。

不需要每次将所有历史问答完整输入模型。

允许使用近期记录、与当前困难相关的历史记录及轻量结构化历史摘要控制上下文规模。

不新增独立向量检索或长期记忆服务。

### 7.4 Agent 调用节点与自主干预时机

区分两个概念：

- 系统提供 Agent 观察机会的时机。
- Agent 自主决定是否需要教学干预的时机。

在轻量 Demo 范围内，由程序提供有限的观察节点。

建议包括：

1. 用户主动进入下一学习日，今日学习记录已保存时。
2. 用户在 AI 助手中提交具有新学习反馈的问题，且当前有相关学习任务时。

第二类观察节点可以复用现有问答流程或采用轻量合并机制，避免每次对话都重复执行完整 Agent 推理。

普通任务勾选操作不需要立即触发模型调用。

Agent 在获得观察机会后，自主判断：

- 当前是否存在值得干预的问题。
- 现有证据是否充分。
- 是否需要继续观察。
- 是否需要立即给予教学帮助。
- 是否需要修改当前或后续学习安排。
- 是否需要通过 AI 助手向用户进一步了解情况。

不得通过固定的“连续 N 天未完成就强制调整”规则替代 Agent 的教学判断。

连续未完成次数、重复提问次数等可以作为观察事实，但不应被直接等同于必须采取的行动。

### 7.5 Agent 教学决策原则

Agent 应遵循以下原则：

1. 默认保持原有教学计划。
2. 单次任务未完成、单次普通提问或偶尔漏练，不应自动引发计划调整。
3. 优先区分用户没有时间、没有执行、没有理解和无法熟练完成等不同情况。
4. 当用户明确表达严重学习困难时，可以及时干预，不必等待多个学习日。
5. 对于证据不足的问题，可以继续观察或请求澄清。
6. 当重复困难持续存在、原有教学方法明显无效，或当前任务不适合用户时，再考虑调整。
7. 优先使用成本较低、影响范围较小的教学行动。
8. 已经提供过的解释或调整方案，应结合后续反馈判断是否有效，避免反复提供相同建议。
9. 不因用户一次自评良好就直接认定其已经掌握技能。
10. 不以提高表面任务完成率为目的，随意降低重要学习要求。
11. 不对已经完成的历史记录进行覆盖或删除。
12. 不在没有充分理由的情况下重新生成整个学习路线。

以上为教学决策约束，不是预先写死的行动分支。

具体问题诊断、干预时机及行动选择由模型结合上下文自主判断。

### 7.6 Agent 可选行动

在明确的有限行动空间内，由 Agent 自主选择适当行动。

#### Action 1：保持计划（KEEP_PLAN）

判断没有充分理由进行干预，保持当前学习路线和练习安排。

这是正常、合理且应当经常出现的 Agent 决策结果。

无需向用户展示重复的“计划无需调整”消息。

#### Action 2：教学提示（GUIDE）

根据用户困难提供针对性的学习提示、注意事项或新的讲解方式。

适用于通过少量指导即可改善学习的问题。

可以复用现有 AI 助手及资料检索能力。

不修改任务计划。

#### Action 3：请求澄清（CLARIFY）

当 Agent 无法判断任务未完成的真实原因时，通过简短问题了解用户情况。

例如：

“你最近没有完成和弦转换练习，是因为时间不够，还是转换动作本身比较困难？”

不得频繁询问用户已经提供过的信息。

#### Action 4：任务拆解（DECOMPOSE_TASK）

当用户面对某项任务存在明确困难时，将原任务拆分为更容易执行的子任务。

例如将完整和弦转换练习拆分为：

- 单个和弦手指定位。
- 两个和弦之间的慢速转换。
- 在保持准确性的前提下逐渐提高速度。

拆解后的任务需要保留原始学习目标、必要依赖关系及相关资料依据。

#### Action 5：调整练习（ADJUST_PRACTICE）

根据学习反馈修改周期性练习任务的部分属性，包括：

- 单次练习时长。
- 练习频率。
- 练习难度。
- 练习步骤。
- 建议复核时机。

仅调整必要的部分。

#### Action 6：调整任务安排（RESCHEDULE）

在合理范围内调整后续任务的顺序或执行时间。

例如：

- 暂缓依赖尚未掌握能力的任务。
- 提前安排不依赖当前困难技能的任务。
- 降低近期任务负担。
- 安排已经学过但需要重新巩固的内容。

不得绕过必要的前置依赖关系。

#### Action 7：建议掌握检验（CHECK_MASTERY）

在用户表示已经熟练掌握某项能力，或 Agent 需要进一步了解学习效果时，生成一个简单的自我检验任务。

本版本不实现专业音视频能力评分。

检验结果仅作为用户自评或有限检验结果使用，不应被描述为客观、专业的技能认证。

### 7.7 Agent 自主执行机制

Agent 需要具备真实的有限自治行动能力，而不是仅输出一段教学建议或返回分类标签。

采用以下轻量决策循环：

观察学习状态

→ 判断是否存在需要处理的问题

→ 自主选择行动

→ 调用允许的行动能力

→ 获取行动执行结果

→ 判断是否继续行动、等待用户反馈或结束本轮决策。

Agent 可以在允许范围内调用现有资料检索、教学提示、任务拆解、练习调整、任务安排等能力。

具体实现可以使用现有模型支持的工具调用机制，也可以采用模型结构化行动输出与程序执行器结合的方式。

不强制引入新的 Agent 框架。

每轮只允许少量工具调用，建议最多 3 次，并设置明确的结束条件及异常退出机制。

需要区分：

- 本轮行动执行结果：如任务调整是否通过程序校验。
- 后续教学效果反馈：如用户在下一学习日是否能够完成调整后的任务。

Agent 不应在用户尚未完成实际练习的情况下，自行推断教学干预已经成功。

等待用户下一次学习或反馈，本身可以是合法的结束状态。

### 7.8 Agent 决策输出

Agent 每次教学决策应具有可供程序处理的结构化结果。

建议表达以下信息：

- 是否需要教学干预。
- 当前观察到的主要问题。
- 判断所依据的真实学习记录。
- 所选行动。
- 行动目标任务。
- 行动参数及具体变更内容。
- 简短、可向用户展示的调整原因。
- 是否需要用户确认。
- 是否结束本轮决策或等待后续反馈。

不要求保存或展示模型内部的完整推理过程。

保存简洁、可审查的决策依据和行动结果即可。

Agent 不得引用不存在的任务、学习记录或用户反馈作为决策依据。

### 7.9 Agent 权限边界

Agent 可以：

- 主动决定是否需要教学干预。
- 自主选择允许的教学行动。
- 提供教学提示。
- 请求必要澄清。
- 在规则允许范围内生成局部任务调整。
- 对后续学习安排提出并执行有限变更。

Agent 不可以：

- 擅自改变用户的整体学习目标。
- 删除用户原始资料。
- 覆盖已经发生的学习历史。
- 将未完成任务直接标记为完成。
- 凭空认定用户已经掌握某项技能。
- 无限制地重新生成整个学习计划。
- 调用未经授权的外部工具。
- 执行无限循环或无限重试。
- 脱离当前学习主题执行无关任务。

所有任务变更必须经过程序校验。

对于影响范围较小、可撤销的调整，例如缩短练习时长或补充一个简单练习，可以自动生效，并向用户说明。

对于影响学习主线、关键前置依赖、重要任务移除等较大变更，应先生成调整方案并等待用户确认。

用户确认不是代替 Agent 自主决策，而是对高影响行动的权限约束。

### 7.10 防止过度干预

Agent 需要读取此前已经执行的教学干预及后续学习反馈。

如果某项任务刚刚完成调整，而用户尚未实际执行调整后的任务，默认不应再次修改该任务。

除非用户明确反馈新的严重困难，或此前调整存在明显问题。

不需要建立复杂的冷却时间系统或固定干预次数规则。

通过模型决策约束、历史行动状态和有限的程序保护机制实现稳定教学。

## 8. 功能需求四：Agent 教学交互

### 8.1 产品交互原则

Agent 应融入现有学习流程，而不是新增一个独立的复杂 Agent 操作页面。

用户不需要理解 Agent、Workflow、Tool、State 等技术概念。

用户只需要感知到 AI 老师能够了解自己的学习情况，在有必要时提供更适合自己的学习安排。

### 8.2 教学提示展示

Agent 认为需要给予指导但不需要修改计划时，可以在当前学习页面或 AI 助手中展示简短教学提示。

例如：

“你最近几次都在询问和弦转换时的手指定位问题。建议先放慢速度，确保每个和弦的手指位置正确，再进行连续转换。”

提示应关联具体任务。

避免无依据的鼓励、过度总结或每天重复生成教学寄语。

### 8.3 学习计划调整展示

当 Agent 对学习安排进行调整时，在今日学习页面展示轻量调整提示。

至少让用户理解：

- 为什么进行了调整。
- 哪些任务发生了变化。
- 新的学习安排是什么。

示例：

**AI 老师调整了你的练习安排**

你近期多次询问 C 和弦与 G 和弦的转换问题，并且相关练习尚未完成。

为了降低练习难度，已将原来的连续和弦转换练习拆分为单个和弦定位和慢速转换两个练习。歌曲弹唱任务暂缓，其他学习任务保持不变。

用户能够查看调整内容，并撤销尚未产生后续学习记录的低影响调整。

如果调整已经产生新的学习记录，应保留历史，通过新的计划变更恢复安排，而不是回滚或删除历史。

### 8.4 请求澄清

如果 Agent 需要了解用户无法完成任务的原因，优先复用现有 AI 助手交互。

用户可以回答，也可以暂时忽略。

当用户没有回应时，默认维持原有学习计划或安全的已有安排，不阻止用户继续使用产品。

### 8.5 用户确认

对于需要确认的高影响调整，提供简洁的接受或拒绝操作。

用户拒绝时保留当前有效计划。

Agent 应记录该行动未被接受，避免在没有新证据的情况下反复提出相同调整。

### 8.6 无干预状态

如果 Agent 判断暂时不需要进行教学干预，用户正常进入后续学习日。

不额外增加页面操作步骤，不展示技术决策日志，不打断正常学习。

## 9. 数据与状态管理

### 9.1 数据结构

在现有学习计划及学习进度数据基础上，补充以下逻辑数据。

具体字段及存储实现由 Codex 根据已有项目架构确定。

**A. 初始学习计划**

保存 Workflow 最初生成的学习路线及任务安排，作为原始计划参考。

**B. 当前有效学习计划**

表示经过 Agent 局部调整后，当前实际使用的任务结构和调度配置。

**C. 学习日记录**

记录学习日编号、开始时间、每日任务实例、任务完成状态及相关时间信息。

**D. AI 问答历史**

关联学习日及学习任务，作为 Agent 判断学习困难的重要依据。

**E. Agent 决策记录**

保存观察依据、所选行动、执行结果及终止状态等必要信息。

**F. 学习计划调整记录**

保存调整前后差异、调整原因、关联任务、用户确认状态和生效时间。

### 9.2 状态一致性

需要保证以下规则：

- 初始学习计划能够与当前有效学习计划区分。
- 学习计划调整不能覆盖已经发生的历史学习记录。
- 周期任务的单日完成状态与长期练习状态相互独立。
- 用户进入下一学习日时，之前的记录正确保存。
- 页面刷新后，学习进度、问答历史及有效计划能够正确恢复。
- Agent 调整失败时，不污染现有学习状态。
- 同一学习日切换操作或同一 Agent 行动不得重复应用。

### 9.3 存储要求

优先沿用现有项目的轻量存储方案。

不因为引入学习历史及 Agent 决策记录而强制增加新的数据库或后端基础设施。

对旧版数据进行必要的兼容处理，避免因新增任务类型导致现有学习计划无法读取。

## 10. 异常处理与降级

### 10.1 Agent 调用失败

如果 Agent 请求失败、超时或输出不可用：

- 保留当前有效学习计划。
- 保留用户已有学习记录。
- 使用确定性程序逻辑生成后续每日任务。
- 不阻止用户进入下一学习日。
- 保存必要的异常信息。
- 不将失败的 Agent 调整描述为已成功执行。

Agent 是提升教学适应性的能力，不应成为整个学习流程的单点故障。

### 10.2 无效行动

如果 Agent 返回不存在的任务 ID、非法参数、不合理的任务依赖或超出权限的操作：

- 拒绝执行该行动。
- 保持原有学习计划。
- 允许 Agent 在本轮有限调用预算内修正。
- 超过预算后终止本轮决策。

### 10.3 学习状态不足

当缺少足够学习历史时，Agent 可以：

- 保持原有计划。
- 请求必要澄清。
- 基于明确的即时反馈提供局部帮助。

不得虚构历史学习行为。

### 10.4 重复与并发操作

避免用户重复点击进入下一日、重复提交反馈或重复接受调整时产生：

- 重复学习日。
- 重复任务实例。
- 重复 Agent 调用。
- 重复计划变更。
- 学习状态不一致。

使用现有架构中合适的轻量保护手段实现。

## 11. 典型用户场景

以下为功能逻辑示例，不是需要写死的 Agent 决策规则。

### 场景一：正常持续学习

用户学习吉他，每天完成基础指法练习，同时学习新的乐理知识。

系统在后续学习日继续安排周期练习。

Agent 观察到用户学习正常，没有明显困难，因此保持原有计划。

### 场景二：偶尔没有完成今日任务

用户 Day 2 因时间不足，只完成部分任务，随后主动进入 Day 3。

系统保存 Day 2 的真实完成情况，正常生成 Day 3 任务。

Agent 可以保持原有计划，不因为一次漏练立即进行教学干预。

### 场景三：反复遇到同一个学习困难

用户连续多个学习日未完成和弦转换练习，并多次在 AI 助手中询问手指定位及转换速度问题。

Agent 综合未完成记录和问答历史，判断用户可能需要更小的练习步骤。

Agent 自主选择任务拆解或调整练习等行动，并在必要时调整后续任务安排。

调整后继续观察用户实际学习情况。

### 场景四：用户明确表示当前任务无法完成

用户通过 AI 助手表示：

“这个练习对我来说太难了，我完全不知道怎么做。”

即使用户没有积累多个学习日的失败记录，Agent 也可以判断当前存在需要及时处理的问题。

Agent 根据具体内容选择重新讲解、请求澄清、拆解任务或其他合理行动。

### 场景五：重复练习但无法判断是否掌握

用户多次完成基础练习，并表示已经比较熟练。

Agent 可以选择建议掌握检验，而不是直接认定用户已经掌握技能。

在获得进一步反馈后，再判断是否调整练习频率或后续任务安排。

### 场景六：Agent 调整后继续观察

Agent 已经将原本较难的练习拆分为两个简单任务。

用户尚未执行新的练习。

Agent 不应因为历史困难仍然存在而再次拆解任务。

应等待调整后的实际学习反馈，再决定下一步行动。

### 场景七：Agent 不可用

用户完成部分任务后进入下一学习日，但 Agent 服务请求失败。

系统仍然根据当前有效计划生成后续学习任务，用户能够正常继续学习。

## 12. 技术实现约束

1. 继续使用现有 DeepSeek API 和现有模型配置机制。
2. 复用现有资料理解、学习规划、独立核验和轻量 RAG 能力。
3. 不新增模型供应商及 API Key，除非现有能力确实无法满足需求，并有明确的技术依据。
4. 优先通过已有模型调用及轻量程序逻辑实现有限自治 Agent。
5. 不强制引入 LangChain、LangGraph 或其他 Agent 框架。
6. 不采用多 Agent 架构。
7. 不额外建立复杂的记忆数据库、知识图谱或事件系统。
8. 控制 Agent 上下文大小和单轮工具调用数量。
9. 不在页面渲染、普通任务勾选或无状态变化时重复调用模型。
10. 不为展示 Agent 能力而将确定性程序逻辑交给大模型。
11. 保持现有资料溯源机制及内容边界。
12. 保持 API Key 等敏感配置的现有服务端安全边界。
13. 尽量保持现有项目代码组织方式，避免大规模无关重构。

## 13. 功能验收标准

本阶段仅进行功能验收和必要回归测试，不开展系统化生成质量评测或用户留存实验。

### 13.1 Workflow 验收

- 能够正常接收现有支持的学习资料。
- 能够生成一次性学习任务。
- 能够在适当场景下生成周期性练习任务。
- 不强制所有主题包含周期性任务。
- 周期任务包含合理的调度信息及单次完成标准。
- 任务步骤和资料引用仍然能够正常展示。
- 现有图片识别、主题识别及异常输入处理能力不出现明显回归。

### 13.2 今日学习机制验收

- 学习页面默认展示当前学习日的任务。
- 一次性任务和周期性任务能够正确区分。
- 完成一次性任务后，不会被系统无故重复安排。
- 完成周期性任务后，后续学习日仍可正常出现新的练习实例。
- 今日任务未全部完成时，可以正常进入下一学习日。
- 未完成任务不会被错误标记为完成。
- 未完成任务不会无限累积并占满后续学习安排。
- 必要的前置任务依赖能够得到遵守。
- 历史学习日记录能够正确保存。
- 页面刷新后学习状态能够正常恢复。

### 13.3 Agent 验收

- Agent 能够读取当前与历史任务完成情况。
- Agent 能够读取相关 AI 助手问答历史。
- Agent 能够基于学习状态判断是否需要干预。
- Agent 允许选择保持原计划，而不是必然生成调整。
- Agent 能够自主选择不同的合法教学行动。
- Agent 行动能够真实影响教学内容或后续任务安排，而非仅生成文字描述。
- Agent 能够获取行动执行结果并决定结束、继续或等待反馈。
- 合法计划变更能够正确生效。
- 高影响调整需要用户确认。
- 非法行动能够被拦截。
- Agent 不会无限循环调用。
- Agent 请求失败时，用户仍然可以继续学习。
- Agent 决策及计划变更记录能够保存。

真实模型功能验收应至少演示不干预、局部教学干预和任务调整三种不同路径，不能只使用 Mock 数据证明 Agent 已经接通。

以上验收用于确认机制已经实现，不代表 Agent 决策准确率及用户价值已经通过系统化验证。

- 学习资料输入。
- 真实 AI 分析。
- 学习路线生成。
- 学习任务展示。
- 原始资料查看与引用定位。
- 基于学习上下文的 AI 答疑。
- 轻量 RAG 与溯源回答。
- 学习进度管理。
